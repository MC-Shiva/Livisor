# 用語集（ユビキタス言語）

チームが会話で使っている言葉と、Livisor.Server・Livisor.Shared のコード名の対応表。会話・ドキュメント・レビューでは「用語」列の言葉か、併記した別名を使う。コード名は英語のまま書く。
概念や契約を変えるときは、この表とコードの対応を一緒に更新する。「決定」と書いたものはチームで決めた内容。それ以外の細則は実装上の判断。

「コード」列の注記: Domain = サーバー内部の業務ルールを表す型、DTO = 通信で運ぶデータの型、Entity = 識別子（room）で区別する型。

## 役割と単位

| 用語 | 意味 | コード |
|---|---|---|
| 管理者（アドミン、DJ） | 再生・停止・スケジューリング・音量を操作する役割の人。利用上の役割であり、コード上では権限を区別せず、誰でも操作を呼び出せる。ハッカソン主催側の「運営」とは別 | — |
| 管理者画面 | 管理者がサーバーへ操作を送る画面（Unity 製）。サーバーから見ると、Unary サービスと StreamingHub を利用するアプリの 1 つ | — |
| クライアント | 観客が使う VR アプリ（Unity）。サーバーから状態の差分とトランスポートを受け取り、音や演出に反映する。振動デバイスとは別の構成要素 | — |
| 観客 | VR で公演を見る人。利用上の役割 | — |
| 参加中のクライアント接続 | room の配信グループに入っている 1 本の接続。会話では「コネクション」。配信の単位は人ではなく接続 | `RoomGroupProvider`、`ConnectionId` |
| room（ルーム） | 状態を保持し配信する単位。公演との対応は運用で決める（いまは 1 公演 = 1 room の想定） | `RoomId`、`Room`（Entity） |
| サーバー時刻 | サーバーが取得した時刻。1970 年 1 月 1 日 0 時 0 分 0 秒（UTC、世界共通の時刻基準）からの経過ミリ秒で表す。会話では「サーバーの時間」。再生開始時刻と、応答・通知用のデータを作った時点の時刻に使う。今回の簡易計算では、クライアントの時計との差を使った補正はしない | `IClock`、`TransportState.StartedAtServerMs` / `ServerTimeMs`、`RoomStatePatch.ServerTimeMs` |
| 疎通確認 | サーバーとクライアントの間で、再生指示・予約アクション・音量が届くことを確かめること。受信側で反映されることも確かめる。接続できただけでは疎通確認と言わない。全体の疎通確認の合格ライン（決定） | — |

## 通信の分担（決定）

| 用語 | 意味 | コード |
|---|---|---|
| Unary サービス | 1 回の要求に 1 回の応答を返す通信。再生・停止・スケジューリングの要求を受け付ける。要求を受けずにクライアントへ通知する用途には使わない | `ITimelineService`、`TimelineService` |
| StreamingHub | 接続を保ち、サーバーとクライアントが互いにデータを送る通信。このシステムでは、状態の差分（更新対象の項目）とトランスポート（再生状態）をサーバーから通知する経路として使う | `IRoomStateHub`、`RoomStateHub` |
| スケジューリング | 「再生開始から相対時間 t 後にこのアクションを実行する」を登録すること。登録した 1 件を **予約アクション** と呼ぶ。登録は 1 回の操作で済むため、Unary サービスで受け付ける | `ITimelineService.ScheduleActionAsync`、`ScheduledAction` |
| 状態同期 | 心拍数・音量・照明の色など、変わり続ける値を同じ room の全員で共有すること。受信したらすぐ反映する。「即時反映」とも言う。厳密な同時再生までは意味しない | `IRoomStateHub`、`RoomState` |
| 受信契約 | サーバーからの通知を受けたときに、クライアント側で動く処理の取り決め。状態の差分とトランスポートの 2 種類 | `IRoomStateHubReceiver.OnStateChanged` / `OnTransportChanged` |
| 配信 | 同じ room の配信グループに参加している全接続へデータを届けること。会話では「ブロードキャスト」とも言う（同じ意味）。送信元の接続にも届く | `RoomGroupProvider.PublishState` / `PublishTransport` |
| 配信グループ | 同じ room に StreamingHub で参加している接続の集まり。Unary サービスで受け付けた操作の結果も、この配信グループを通じて全接続に届ける | `RoomGroupProvider` |

## 再生まわり

| 用語 | 意味 | コード |
|---|---|---|
| トランスポート | 再生・停止の操作と、その再生状態。会話では「再生・停止」「再生状態」。`Transport` は「再生中かどうか」と「再生を開始したサーバー時刻」を持つ。通知用の `TransportState` は、この 2 項目にサーバー時刻と予約アクションを加えたもの。この実装では、再生位置を移動する操作（シーク）を提供しない | `Transport`（Domain）、`TransportState`（DTO）、`TransportMapper` |
| 再生開始 | 再生を開始する操作。停止中なら、サーバーが再生開始時刻を決める（決定）。再生中に再度指示しても開始時刻は変わらない（実装判断） | `ITimelineService.PlayAsync`、`Transport.Start`、`Transport.Playing`（再生中は `true`） |
| 停止 | 再生を止める操作。開始時刻は失われ、次の再生開始で新しい開始時刻になる。予約アクションは取り消さない。再び再生すると、同じ相対時間でクライアントが実行する（決定） | `ITimelineService.StopAsync`、`Transport.Stop` |
| 相対時間 | 再生開始を `00:00:00:00` とした経過時間。表記は `HH:mm:ss:ff`（時:分:秒:センチ秒。センチ秒 = 100 分の 1 秒）。予約アクションの時刻はこれで指定する（決定） | `PlaybackTime`、`TimelineAction.Time` |
| 予約アクション | スケジューリングで登録した 1 件。room ごとに最大 1 件で、新しく登録するとそれまでの 1 件を置き換える（決定）。予約アクションはクライアントが実行する | `ScheduledAction`（Domain）、`Room.Schedule` |
| 予約の取消 | 予約アクションを取り消す操作。再生状態と状態同期は保つ | `ITimelineService.CancelScheduledActionAsync`、`Room.CancelSchedule` |
| アクション | `TimelineAction` で表す操作の種類と値。`play` は真偽値（`true` = 再生、`false` = 停止）、`volumeChange` は整数。通常の音量操作は予約ではなく状態同期の `volume` で即時に反映する（決定）。`volumeChange` の予約は、再生開始から時間 t が経過したときに音量を変えるために使う | `TimelineAction`、`ActionType`、`ActionValue` |
| 発火 | 再生中に、予約アクションの相対時間に達したときクライアントがそれを実行すること。送信時点の再生位置は `ServerTimeMs - StartedAtServerMs` で求める。待ち時間は、予約アクションの相対時間からこの再生位置を引く簡易計算で求める。この計算は通信の遅れを補正しない。遅延対策は今回扱わない（決定）。停止の通知を受けたらタイマーを取り消し、次の再生開始で設定し直す | （クライアント側。式は `TransportState` のコメント） |
| 再生位置 | 再生開始からの経過時間。この実装では独立した項目として保持・送信しない。再生中は、送信時点の位置を `ServerTimeMs - StartedAtServerMs` で求める | `Transport.PositionMs`（テスト用）、`TransportState` |

## 状態同期まわり

| 用語 | 意味 | コード |
|---|---|---|
| 状態（room の状態） | 状態同期で共有する値の集合。キー（項目名）と値の組で持つ。正式な再生状態は `TransportState` に集約し、`RoomState` では `playing` を使わない（実装判断） | `RoomState`（Domain） |
| 状態項目 | 状態を構成するキーと値の 1 組 | `RoomStateEntry`（DTO） |
| 状態の差分（パッチ） | 送信側が指定した更新対象の項目だけを載せたもの。サーバーは変更前後を比べない。状態同期の全項目を含むのは、参加時の応答だけ。会話の「差分」は時計のずれや認識のずれにも使うので、この意味では「状態の差分」と言う | `RoomStatePatch`（DTO） |
| マージ | 状態の差分に含まれるキーの値を更新すること。含まれないキーの値は保つ。同じ差分に同じキーが複数あれば、最後の値を使う | `RoomState.Merge`、`Room.ApplyState` |
| 既知キー | 値の種類が決まっていて、その種類かどうかを確認するキー。`volume`（音量、整数）と `heartRate`（心拍数、整数）。値の範囲は確認しない | `RoomStateKeys` |
| 未知キー | 既知キー以外のキー。値には整数・真偽値・文字列を使える。照明の色など、公演ごとに項目が増えるため、キーごとに値の種類を制限しない。何も書かれていないキーや空白だけのキーは受け付けない | — |
| 値の種類 | 整数・真偽値・文字列の区分。アクションと状態項目で共通に使う | `ActionValue`、`ActionValueKind` |
| 心拍数 | 観客の心拍数。状態同期の `heartRate` で送る想定。測って送る仕組みは今回作らない（決定）。発表では、心拍数を送っているように見せる | `RoomStateKeys.HeartRate` |
| 参加（join） | room の配信グループに入り、状態同期の全項目を受け取ること。参加時の応答にはトランスポートを含まない。必要なら、参加後に `GetTransportAsync` で取得する。別の room に参加すると前の room から離脱する。途中参加者の再生位置を合わせる処理は、今回の対応範囲に含めない（Issue #20） | `IRoomStateHub.JoinAsync`、`ITimelineService.GetTransportAsync` |

## 別名と使い分け

| 言葉 | 扱い |
|---|---|
| ブロードキャスト | 「配信」と同じ意味。文書では「配信」に統一する。コード名に残る `Broadcast`（`CommitAndBroadcast`）はそのまま書く |
| スケジュール、予約 | 「スケジューリング」（登録する操作）と「予約アクション」（登録済みの 1 件）を区別する。どちらの意味で言っているかが分かるように書く |
| タイムライン | 現在の仕組みには無い概念なので使わない。コード名の `ITimelineService`、`TimelineService`、`TimelineAction` は名前だけが残っているもので、中身は再生・停止・予約アクションの受け口 |
| 絶対時間、絶対時刻 | 予約アクションの指定には使わない（相対時間で指定する）。再生開始時刻や送信時刻の説明では「サーバー時刻」と言う |
| 同期 | 意味が 6 つある（一緒に見る、演出が連動する、値を共有する、他の観客の位置を合わせる、時計を合わせる、同じ瞬間に鳴らす）。値の共有は「状態同期」、時計は「時刻合わせ（クロック差）」、他の観客の位置は「位置同期」（今回はやらない）、演出は「連動」、同じ瞬間に鳴らすことは「同時再生」と言い分ける |
| 遅延、遅延対策 | 時計のずれと通信の遅れを同じ語で呼ばない。時計のずれは「クロック差」、通信の遅れは「通信遅延（片道 / 往復）」。今回はどちらも扱わない。発火の式は受信した瞬間を基準にするので、時計のずれは結果に入らない |
| 疎通確認、接続確認 | 接続できただけなら「接続確認」。データが届いて受信側で反映されるところまで確かめたら「疎通確認」 |
